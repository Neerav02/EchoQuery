# Phase 09: Milestone 2 — Database and Migrations Remediation

## Objective
Fix the confirmed critical fresh-database failure in the initial Alembic migration (`a43181a5d516_initial_schema_and_security.py`) while strictly preserving the existing migration revision chain (`a43181a5d516 -> bb3e66028d93 -> 23a242a11396`), deployed database compatibility, and workspace rules in `.kilocoderules` (`users`, `jobs`, `refresh_tokens`, `outbox_tasks`, `User #1`, `Jobs #1-#3`).

## Execution Context
- **Planning only**: Do not edit migration files or run `alembic` commands during planning.
- **Root cause verified in codebase**:
  - `app/migrations/versions/a43181a5d516_initial_schema_and_security.py` creates `refresh_tokens` (FK -> `users.id`) and `outbox_tasks` (FK -> `jobs.id`), and runs `batch_alter_table` on `jobs` and `users`, assuming `users` and `jobs` already exist from pre-Alembic `Base.metadata.create_all()`. On a fresh database, `alembic upgrade head` fails immediately.
  - `app/migrations/versions/bb3e66028d93_sync_missing_legacy_columns.py` and `app/migrations/versions/23a242a11396_align_schema_nullability_types_and_indexes.py` are currently untracked in Git and expect `a43181a5d516` -> `bb3e66028d93` -> `23a242a11396` continuity.
  - `app/models.py:13` defines `User.email` with `unique=True, index=True, nullable=False`, whereas `23a242a11396` aligns `nullable=False` and `ix_jobs_status` but does not ensure `users.email` uniqueness/index on fresh or migrated schemas.
- **Safety rules**:
  - Never run migrations against the active/existing local database (`echoquery.db` or configured production DB).
  - Use `alembic -x db_url=...` (supported by `app/migrations/env.py`) against a separate disposable database inside temporary directories.

## Task Order & Breakdown

### Task 09-01: Make Initial Migration `a43181a5d516` Fresh-Database Safe (`app/migrations/versions/a43181a5d516_initial_schema_and_security.py`)
- **Order**: 1
- **Dependencies**: None
- **Affected Files**:
  - `app/migrations/versions/a43181a5d516_initial_schema_and_security.py:1-97`
  - Reference: `app/models.py:1-78`
- **Implementation Plan**:
  - Keep `revision = 'a43181a5d516'` and `down_revision = None` unchanged.
  - At the top of `upgrade()`, inspect existing tables via `bind = op.get_bind()` and `inspector = sa.inspect(bind)` (`existing_tables = set(inspector.get_table_names())`).
  - If `'users'` is not in `existing_tables`, create `'users'` with the baseline columns expected by `a43181a5d516`, `bb3e66028d93`, and `23a242a11396` (including `id`, `email`, `hashed_password`, `is_active`, `is_superuser`, `created_at` or letting `batch_alter_table`/subsequent steps remain idempotent without duplicate column errors).
  - If `'jobs'` is not in `existing_tables`, create `'jobs'` with the baseline columns (`id`, `filename`, `storage_name`, `status`, `created_at`, `user_id` FK -> `users.id`, etc.) before creating `refresh_tokens` and `outbox_tasks`.
  - Guard all `op.create_table`, `op.add_column`, and `op.create_index` operations in `a43181a5d516` with inspector existence checks so both paths work seamlessly:
    - **Fresh DB path**: `users` and `jobs` are created cleanly before FK creation in `refresh_tokens` and `outbox_tasks`.
    - **Legacy pre-Alembic DB path**: existing `users` and `jobs` tables are detected, preserved without data loss, and only missing security columns/tables are added.
  - Ensure `downgrade()` handles cleanly and safely without failing on missing columns/tables or accidentally erasing conditional state improperly.
- **Risks & Mitigations**:
  - *Risk*: Adding a column twice (once during conditional `users`/`jobs` creation in `a43181a5d516` and again in `a43181a5d516`'s `batch_alter_table` or `bb3e66028d93`) causes `DuplicateColumnError` on fresh DBs.
    - *Mitigation*: Explicitly check `inspector.get_columns(table_name)` (already started in `bb3e66028d93`) before any `add_column` in `a43181a5d516`.
  - *Risk*: Breaking `alembic upgrade head --sql` (offline mode) if `op.get_bind()` inspection is called during offline SQL generation.
    - *Mitigation*: Check `context.is_offline_mode()` — in offline mode, assume fresh schema generation or avoid `sa.inspect(bind)` calls that fail on mock/offline connections.
- **Acceptance Criteria**:
  1. `revision` remains `'a43181a5d516'` with `down_revision = None`.
  2. On an empty disposable database, running `alembic upgrade a43181a5d516` creates `users`, `jobs`, `refresh_tokens`, and `outbox_tasks` without errors.
  3. On a legacy database pre-seeded with pre-Alembic `users` (`User #1`) and `jobs` (`Jobs #1-#3`), running `alembic upgrade a43181a5d516` preserves all rows and upgrades cleanly.
