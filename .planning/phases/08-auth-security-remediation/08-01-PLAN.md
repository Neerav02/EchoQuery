# Phase 08: Milestone 1 — Authentication and Security Remediation

## Objective
Eliminate the two confirmed critical security vulnerabilities in EchoQuery v2.0 without breaking existing development/test workflows or the FastAPI/SQLAlchemy/Redis architecture:
1. Enforce non-default, strong `JWT_SECRET_KEY` configuration when `ENVIRONMENT` is `production`.
2. Require JWT authentication and job-ownership authorization on `/ws/stream/{job_id}` consistent with HTTP endpoints such as `GET /jobs/{job_id}`.

## Execution Context
- **Planning only**: Do not modify application code, `.env`, or run database migrations during planning.
- **Architectural invariants**:
  - Preserve `Settings(BaseSettings)` in `app/config.py` and existing token helpers (`decode_token`, `is_token_blacklisted`) in `app/security.py`.
  - Preserve `ConnectionManager` and `GET /jobs/{job_id}` ownership rules in `app/main.py:461-464`.
- **Cross-milestone interactions**:
  - **Phase 10 (Docker & Infrastructure)**: Any Compose/container deployment running with `ENVIRONMENT=production` must supply a valid 32+ byte `JWT_SECRET_KEY` via runtime environment injection.
  - **Phase 11 (Test Reliability)**: Securing `/ws/stream/{job_id}` directly affects `app/tests/test_distributed_streaming.py:66-73` (`test_websocket_stream_receives_events`), which currently connects unauthenticated to `job_id = 903`.

## Task Order & Breakdown

### Task 08-01: Production JWT Secret Validation (`app/config.py`)
- **Order**: 1 (foundational config safety; no upstream task dependency)
- **Dependencies**: None
- **Affected Files**:
  - `app/config.py:9` (`ENVIRONMENT: str = "development"`)
  - `app/config.py:18-20` (`JWT_SECRET_KEY`, `JWT_SECRET_KEY_FALLBACK`, `JWT_ALGORITHM`)
- **Implementation Plan**:
  - Track the hardcoded default placeholder (`"echoquery-production-secret-key-minimum-32-bytes-secure!"`) as a constant or known insecure default inside `app/config.py`.
  - Add a Pydantic `model_validator(mode="after")` on `Settings` that normalizes `ENVIRONMENT.strip().lower()` and checks when `ENVIRONMENT == "production"`:
    - `JWT_SECRET_KEY` must not be empty, whitespace-only, or equal to the default placeholder.
    - `len(JWT_SECRET_KEY.encode("utf-8")) >= 32` (minimum 32-byte HS256 secret length).
    - If `JWT_SECRET_KEY_FALLBACK` is set, ensure it is also non-default / >= 32 bytes if non-empty.
  - Raise a clear `ValueError` referencing `JWT_SECRET_KEY` and `ENVIRONMENT=production` (never logging secret values).
- **Risks & Mitigations**:
  - *Risk*: Breaking local dev, CI, or `pytest` runs where `ENVIRONMENT` defaults to `"development"` or `"test"`.
    - *Mitigation*: Enforce strict rejection only when `ENVIRONMENT.strip().lower() == "production"`.
  - *Risk*: Docker Compose or PaaS deployments setting `ENVIRONMENT=production` without setting `JWT_SECRET_KEY` will intentionally fail fast at startup.
    - *Mitigation*: Document required runtime secret injection in Phase 10 acceptance criteria; do not hardcode secrets in Compose/Dockerfiles.
- **Acceptance Criteria**:
  1. Instantiating `Settings(ENVIRONMENT="production")` without overriding `JWT_SECRET_KEY` raises `ValidationError` / `ValueError`.
  2. Instantiating `Settings(ENVIRONMENT="production", JWT_SECRET_KEY="short")` raises `ValidationError` / `ValueError`.
  3. Instantiating `Settings(ENVIRONMENT="production", JWT_SECRET_KEY=<32+ byte non-default secret>)` succeeds.
  4. Instantiating `Settings(ENVIRONMENT="development")` and `Settings(ENVIRONMENT="test")` with default settings succeeds without regression.

### Task 08-02: WebSocket Authentication and Job Ownership Authorization (`app/main.py`)
- **Order**: 2 (executes alongside or right after 08-01)
- **Dependencies**: Task `08-01` (consistent JWT config validation); uses existing `decode_token`, `is_token_blacklisted` from `app/security.py` and `Job`/`User` models from `app/models.py`.
- **Affected Files**:
  - `app/main.py:114-152` (`get_current_user`, `require_current_user`, `require_admin`)
  - `app/main.py:450-481` (`get_job_status` ownership pattern at lines 461-464)
  - `app/main.py:605-653` (`websocket_stream_endpoint`)
- **Implementation Plan**:
  - Extract token from the WebSocket handshake: accept either `Authorization: Bearer <token>` header or a `token` query parameter (standard browser WebSocket clients cannot set custom `Authorization` headers, while API/CLI clients may use either). Never accept unsigned or malformed tokens.
  - Validate the JWT using `decode_token` and verify it is an `"access"` token (matching HTTP `get_current_user` semantics) and not blacklisted via `is_token_blacklisted`.
  - Look up the active `User` (`is_active == True`) using a short-lived DB session (and close/release the DB session promptly before entering the long-lived Redis streaming loop so DB pool connections are not held open for the duration of the WebSocket).
  - Verify `job_id` parses cleanly as a job identifier (if numeric ID expected, reject invalid IDs cleanly) and load the `Job` record:
    - If job does not exist, reject/close with policy/unauthorized close code (`WS_1008_POLICY_VIOLATION` or close prior to/immediately on reject without leaking job existence details beyond standard policy).
    - Enforce uniform job authorization (`can_access_job`): deny whenever `current_user is None`; if `job.user_id is None` (ownerless job), allow only `current_user.is_superuser`; if `job.user_id is not None`, require `current_user.id == job.user_id` or `current_user.is_superuser`.
  - Reject unauthenticated/unauthorized connections before calling `manager.connect(websocket, job_id)` (e.g., `await websocket.close(code=status.WS_1008_POLICY_VIOLATION)` and return), ensuring no stream replay or live pub/sub events are ever sent.
- **Risks & Mitigations**:
  - *Risk*: Holding a SQLAlchemy `Session` open across a long-lived WebSocket loop exhausts the connection pool under concurrent clients.
    - *Mitigation*: Perform token + user + job ownership verification in a scoped `with SessionLocal() as db:` (or `db.close()` in `finally`) before calling `manager.connect(...)`.
  - *Risk*: Query-string tokens can appear in reverse-proxy access logs if not noted.
    - *Mitigation*: Support `Authorization: Bearer` header first and `token` query parameter as WebSocket browser fallback, and avoid logging raw query strings/tokens in application logs.
  - *Risk*: Breaking existing WebSocket tests or clients expecting unauthenticated `ws://.../ws/stream/903`.
    - *Mitigation*: Coordinate directly with Task `08-03` and Phase 11 (`test_distributed_streaming.py`).
- **Acceptance Criteria**:
  1. Unauthenticated connection to `/ws/stream/{job_id}` is rejected with WebSocket close code `1008` and receives zero stream events.
  2. Connection with malformed, expired, refresh-type, or blacklisted token is rejected with WebSocket close code `1008`.
  3. Authenticated user attempting to connect to another user's `job_id` (when `not current_user.is_superuser`) is rejected with WebSocket close code `1008`.
  4. Authenticated job owner or superuser successfully connects and receives replay + live stream events; DB session is released immediately after handshake authorization.

### Task 08-03: Security & WebSocket Regression Tests (`app/tests/test_security.py`, `app/tests/test_distributed_streaming.py`)
- **Order**: 3
- **Dependencies**: Tasks `08-01` and `08-02`
- **Affected Files**:
  - `app/tests/test_security.py`
  - `app/tests/test_distributed_streaming.py:66-73`
- **Implementation Plan**:
  - Add unit tests in `app/tests/test_security.py` verifying:
    - `Settings` rejects default placeholder and `< 32`-byte `JWT_SECRET_KEY` when `ENVIRONMENT="production"`.
    - `Settings` accepts valid `>= 32`-byte non-default secret in `production`, and keeps default behavior in `development`/`test`.
    - `/ws/stream/{job_id}` rejects: missing token, invalid/expired/blacklisted token, nonexistent job, and non-owner non-superuser user.
    - `/ws/stream/{job_id}` allows job owner and superuser (both `Authorization: Bearer` header and `?token=` query parameter).
  - Update `test_websocket_stream_receives_events` in `app/tests/test_distributed_streaming.py:66-73` to create/seed a test `User` and `Job` owned by that user (instead of raw unauthenticated `job_id = 903`), mint an access token via `create_access_token`, and connect with valid auth credentials.
- **Risks & Mitigations**:
  - *Risk*: Test database state leaking between tests or touching a live database.
    - *Mitigation*: Use existing `conftest.py` isolated SQLite test fixtures / temporary session overrides.
- **Acceptance Criteria**:
  1. All new security and WebSocket authorization tests pass in `pytest`.
  2. `test_distributed_streaming.py` passes with authenticated owner WebSocket connection without mocking away auth dependencies.
  3. Zero regressions across existing `app/tests/test_security.py` and `app/tests/test_main.py` suites.
